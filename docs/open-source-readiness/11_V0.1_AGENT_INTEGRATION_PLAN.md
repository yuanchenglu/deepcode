## 1. 集成目标

在 v0.1 CLI Alpha 稳定后，将 oh-my-deepagent 作为 DeepCode 的预装插件能力交付：

```text
DeepCode Installation
└── Built-in oh-my-deepagent Plugin
    ├── Roles
    ├── Skills
    ├── Planning
    ├── Delegation
    ├── Subagents
    ├── Multi-Agent Orchestration
    ├── Compatibility/Test Runtime（如经审计需要）
    └── Plugin Tests
```

用户不需要单独安装另一个项目，但插件仍可以保持清晰的 Package、API 和内部架构。

当前事实：Package、Runtime 和 13 个 Role 定义存在，但尚未证明被 DeepCode CLI、Gateway 或安装产物调用。因此本图是 v0.2 目标，不是当前生产架构。

## 2. 纠正后的原则

### 2.1 宿主与插件共生

- DeepCode/OpenCode 是宿主。
- oh-my-deepagent 是增强宿主 Agent 能力的插件。
- 插件可以有自己的消息循环、状态机、Subagent 管理和编排逻辑。
- 不把“存在 AgentRuntime”自动判断为架构冲突。

### 2.2 宿主治理真实副作用

插件发起真实代码修改或 Shell 时，必须遵守产品定义的：

- Permission；
- Workspace Policy；
- 用户确认；
- 审计和 Evidence；
- Cancel/Timeout。

实现方式应根据原始插件 API 和当前 Host API 审计决定，不预先强制所有内部代码合并为同一个类。

### 2.3 允许插件状态

插件可维护：

- Orchestration State；
- Parent/Subagent 关系；
- Role 工作状态；
- Scratch Memory；
- Plan/Review 状态；
- 独立测试 Fixture。

需要避免的是同一正式会话存在两个无法协调的权威状态源，而不是禁止插件拥有 MemoryStore。

## 3. 当前已知实现

当前 `packages/oh-my-deepagent` 暴露或包含：

- `AgentRuntime`；
- `runMessageLoop`；
- `ToolRunner`；
- `MemoryStore`；
- Role/Skill/Planning；
- OpenAI/Anthropic Compatible Provider；
- InProcess/HTTP/CLI Transport。

当前不能直接断言这些实现：

- 已用于 DeepCode 生产入口；
- 与宿主冲突；
- 全部需要删除；
- 全部需要替换为宿主实现。

## 5. 角色交付范围

### 5.1 角色清单

目标是让仓库现有角色可随 DeepCode 安装，但不要求一次性全部达到 Stable。准确角色名称、ID、文件、Tool 和 Skill 由 v0.2 审计从源码和 Registry 自动生成，不以人工记忆作为清单。

### 5.2 每个角色的发布标准

1. ID 唯一且稳定。
2. Display Name、Description、适用场景明确。
3. System Prompt 无占位错误。
4. Tool/Skill 契约明确。
5. 权限和 Workspace 行为可验证。
6. 至少一个自动化场景测试。
7. 已知限制有文档。
8. 当前成熟度由证据决定。

### 5.3 核心流程

按以下顺序交付，只有通过门禁的流程才标记正式支持：

- Build；
- Plan；
- Review；
- 用户显式角色选择；
- Plan → Build → Review；
- 角色切换；
- Subagent 委派；
- 结果聚合。

Multi-Agent 的高风险并行写入必须有权限和冲突控制，不能仅靠 Prompt。

## 6. Host-Plugin Contract

### 6.1 Session

明确：

- Host Session ID；
- Plugin Orchestration ID；
- Parent Task / Child Task；
- Workspace；
- Resume/Cancel；
- 历史与工作记忆映射。

### 6.2 Provider

允许的候选形态：

- 插件完全复用 Host Provider；
- 插件通过 Adapter 调用 Host Provider；
- 插件 Provider 保留用于测试或兼容；
- 特殊 Subagent 经明确策略使用独立 Provider。

最终方案由调用图和协议测试决定。

### 6.3 Tool

插件可以保留 ToolRunner 包装器，但生产副作用必须满足宿主安全契约。需要验证：

- Role Tool Filter；
- Skill Tool Filter；
- Permission；
- Workspace/Sandbox；
- Tool Result Settlement；
- Evidence。

### 6.4 Memory

区分 Canonical History、Orchestration State、Subagent Memory 和 Durable Memory。不能简单把所有插件 Memory 归类为重复。

## 7. 测试计划

### 7.1 插件结构测试

- Role Registry；
- Skill Registry；
- Prompt Rendering；
- Tool/Skill 引用；
- 角色元数据；
- Orchestration State。

### 7.2 编排测试

- Plan → Build → Review；
- Parent → Subagent → Aggregate；
- 失败重试；
- 角色切换；
- 多 Agent 冲突处理；
- Cancel 传播。

### 7.3 宿主契约测试

- deny 不可绕过；
- Workspace 外写拒绝；
- 子 Agent 权限不扩大；
- Tool Evidence 可追踪；
- Session/Task 关联正确；
- Provider/Reasoning/Usage 事件可映射。

### 7.4 Compatibility/Test Runtime 测试

若独立 AgentRuntime 被保留为测试或兼容能力，必须：

- 在文档中明确非默认生产入口或其正式用途；
- 有独立测试；
- 不与宿主状态产生隐式冲突；
- 不误导用户需要安装第二个产品。

## 8. 迁移决策门槛

对每个模块按以下顺序决策：

```text
确认调用方
→ 确认原始插件职责
→ 确认产品价值
→ 确认安全契约
→ 选择 Keep/Adapt/Bridge/Replace/Remove
→ 补回归测试
```

在此之前，不执行基于“第二套 Loop”假设的删除。

## 9. 完成标准

- oh-my-deepagent 随 DeepCode 直接可用。
- 宿主与插件职责有文档和测试。
- 插件编排、Subagent 和 Multi-Agent 能力被保留。
- 角色和 Skill 不绕过安全契约。
- 当前独立 Runtime 代码均有准确分类。
- 删除项全部有调用图和替代证据。
- 未达到 Stable 的角色明确标记 Beta/Experimental，不阻塞已验证关键角色发布。
