## 1. 目标

在 v0.1 CLI Alpha 和 v0.2 Agent 集成形成稳定边界后，将现有多平台 Adapter 集合升级为安全、统一、可测试的正式 Gateway 产品能力，并接入 DeepCode Host 与内置 oh-my-deepagent 插件链路。

正确链路：

```text
Platform
→ Adapter Authentication
→ Parse / Normalize
→ Identity / Workspace Policy
→ Host Session / Task Mapping
→ Role Selection / Plugin Orchestration
→ Host-governed Tool Effects
→ Runtime Events
→ Adapter Delivery
```

Gateway 不应复制 Permission、Workspace 和正式任务语义，但可以维护平台鉴权、幂等、Queue、Delivery 和 Session Mapping 状态。

当前代码存在 Adapter/Server/Bridge，但鉴权传递、Queue、回包 Adapter、Session Key 和 Timeout 仍有已确认缺陷，因此不得作为 v0.1 当前能力宣传。

## 2. 与 Agent 插件的关系

Gateway 不是另一个 Agent Runtime。它是入口层：

- 可选择内置 Role；
- 可触发 Plan/Build/Review；
- 可触发 Subagent 或编排流程；
- 通过 Host/Plugin Contract 追踪 Session、Task、Agent 和 Tool；
- 不预设必须绕过或删除 oh-my-deepagent 的 AgentRuntime。

v0.3 实施前应确认当前 Gateway 实际调用：

- CLI 子进程；
- Host API；
- Plugin API；
- Transport；
- 其他 Bridge。

再决定 Adapt、Bridge 或 Replace。

## 3. 禁止链路

```text
无鉴权请求
→ 直接入队
→ 未授权 Workspace
→ 不可追踪 Agent/Tool 副作用
```

以及：

- 固定使用首个 Adapter 回包；
- 无界 Queue；
- 仅以 chatId 作为全局 Session Key；
- Timeout 无法终止实际执行；
- Gateway 自行复制一套不一致的 Permission 语义。

## 5. 安全模型

### 5.1 默认安全

- 默认 disabled。
- 默认 `127.0.0.1`。
- 公网绑定要求显式开启。
- 公网模式必须配置 Adapter Auth、Workspace Allowlist 和 User Policy。
- Enforcement 初始化失败时拒绝启动。

### 5.2 入站鉴权

在解析和入队前验证：

- Signature / Token；
- Timestamp Window；
- Nonce / Message ID；
- Body Integrity；
- Platform Challenge。

失败请求：

- 不入队；
- 不创建 Host Task；
- 不调用插件；
- 不执行 Tool。

### 5.3 Replay / Idempotency

- `(platform, tenant, messageId)` 唯一。
- 重复消息可 ACK，但不重复副作用。
- Store 有 TTL 和容量边界。

## 6. Identity、Session 和 Agent

建议相关性字段：

```text
platform
+ tenant
+ bot
+ user
+ chat
+ thread
+ workspace
+ hostSessionId
+ taskId
+ orchestrationId
+ roleId
```

插件可维护 Parent/Subagent 状态，但 Gateway 必须保留到 Host Task 的映射。

## 7. Queue 和并发

- 同一 Platform Session 保序。
- 不同 Session 可并发。
- Parent/Subagent 并发由插件编排策略管理。
- Gateway Queue 不决定 Agent 权限。
- Cancel/Timeout 必须传播到 Host 和 Plugin。

## 8. Runtime/Transport 策略

当前可能存在 CLI 子进程、HTTP、InProcess 或其他 Transport。处理原则：

1. 先生成当前调用图。
2. 判断 Transport 是生产、兼容还是测试用途。
3. 检查 Timeout、Abort、输出和状态关联。
4. 选择 Keep、Adapt、Bridge、Replace 或 Remove。

不因为插件存在 CLI/HTTP/InProcess Transport 就直接删除；只有不安全、无调用或已被验证替代时才移除。

## 9. 飞书 Stable 目标

必须完成：

- 官方鉴权和 Challenge；
- HTTP/WS 入站；
- 私聊和群聊；
- 多轮 Session；
- Role 选择；
- Agent/Subagent 结果；
- Message Idempotency；
- 超长消息分段；
- 重连和错误恢复；
- 真机 E2E。

## 10. 其他 Adapter 分级

Stable：完整 Auth、Parser、Identity、Workspace、Host/Plugin Path、Outbound 和真机 E2E。

Beta：核心功能和自动化完成，已知限制公开。

Experimental：默认关闭，不宣称生产支持。

## 11. 测试

- Gateway Core Contract。
- Adapter Auth/Replay。
- Session/Role Mapping。
- Gateway → Host → Plugin → Tool → Delivery。
- Parent/Subagent 场景。
- deny/Workspace 不可绕过。
- Timeout/Cancel/Shutdown。

## 12. 发布门槛

- Gateway Core 自动化全绿。
- 飞书真机 E2E。
- 未鉴权请求执行数为 0。
- Session/Task/Agent/Tool 可追踪。
- 无重复副作用。
- 不因错误“单 Loop”假设削弱插件编排。
- Gateway 未通过以上门槛前默认关闭，不进入 Stable 安装制品或官网主张。
