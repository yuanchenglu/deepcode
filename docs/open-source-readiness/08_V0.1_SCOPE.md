# DeepCode v0.1 产品范围冻结

> 状态：Phase 0 已确认，Runtime 边界已勘误
> 分支：`develop`
> 决策日期：2026-07-27
> 目标版本：`v0.1.0`
> 勘误依据：[14_PHASE0_ERRATA_AGENT_RUNTIME.md](./14_PHASE0_ERRATA_AGENT_RUNTIME.md)

## 1. 产品定义

DeepCode v0.1 是一款针对 DeepSeek 深度优化、内置多角色 Agent 插件系统、同时支持本地入口和消息平台入口的开源 Coding Agent。

```text
DeepCode
├── OpenCode-derived Host Runtime
├── Built-in oh-my-deepagent Plugin
├── DeepCode Harness
└── DeepCode Gateway
```

四者共同组成一个产品，但不意味着所有内部模块只能有一条代码循环。

## 2. 已确认的架构决策

### ADR-SCOPE-001 Gateway 进入 v0.1

- Gateway 是 v0.1 一级产品能力。
- Gateway Core 目标 Stable。
- 飞书为首个 Stable Adapter 目标。
- 其他 Adapter 按 Stable、Beta、Experimental 分级。

### ADR-SCOPE-002 oh-my-deepagent 正式内置

- `packages/oh-my-deepagent` 作为 DeepCode 内置插件能力维护。
- 用户不需要将其作为另一个产品单独安装。
- 现有角色全部预装，并逐角色满足发布标准。
- Role、Skill、Planning、Delegation、Subagent 和 Multi-Agent Orchestration 均属于正式产品范围。

### ADR-SCOPE-003 单一宿主执行边界

正确原则是：

> **单一宿主执行边界，允许多个可组合的 Agent 编排循环。**

宿主负责或最终治理：

- 工作区真实副作用；
- Permission 和用户确认；
- 正式 Session/Task 身份；
- Provider 和 Tool 调用的审计；
- Context、History 和 Evidence 的产品级一致性。

插件允许拥有：

- Role 路由；
- Plan → Build → Review；
- Subagent 生命周期；
- 多 Agent 编排；
- 插件级工作记忆；
- 兼容层和测试 Runtime。

### ADR-SCOPE-004 不预设“第二套生产 Loop”

当前源码中存在 `AgentRuntime`、`runMessageLoop`、`ToolRunner`、`MemoryStore`、Provider 和 Transport，只能视为待审计实现事实。

在 Phase 1 调用图和原始插件契约审计前，不得将其直接定性为：

- 与宿主冲突的第二套生产 Runtime；
- 必须删除的重复代码；
- 不允许存在的 Agent Loop。

## 3. v0.1 Must Have

### 3.1 Host Runtime

- DeepSeek OpenAI-compatible Provider Contract。
- Session、Context、History 和 Compaction。
- Tool Call、Tool Result 和流式响应。
- Permission、Workspace、Shell、Abort 和 Evidence。
- CLI/TUI 可完成真实代码任务。

### 3.2 Built-in oh-my-deepagent

- 现有角色随 DeepCode 预装。
- Role/Skill Registry 可发现、可选择、可测试。
- Plan、Build、Review 和高级角色工作流可运行。
- Subagent 和编排机制不得被架构收敛误删。
- 插件调用宿主能力时遵守宿主 Permission、Workspace 和审计契约。
- 插件自有 Runtime/Provider/Memory/Transport 的正式定位经过 Phase 1 审计后确定。

### 3.3 Gateway

- Gateway Core 达到 Stable。
- 默认关闭并默认绑定本地地址。
- 入站鉴权、防重放、幂等、限流、Workspace Allowlist。
- 飞书 Adapter 达到 Stable。
- Gateway 可选择 Role 并进入 DeepCode/oh-my-deepagent 产品链路。

### 3.4 Harness

- Model Routing、Hard Constraints、Reasoning、Scope、Review 至少形成真实 Applied Behavior。
- Harness 决策可追踪。
- 不把日志记录冒充 Enforcement。

### 3.5 Open-source Release

- 一种正式安装方式。
- `bun run check` 或等效统一质量门。
- CI、Secret Scan、Dependency Scan、License Scan。
- README 主张与 Traceability 一致。

## 4. v0.1 非目标

- 云端托管和商业计费。
- 企业多租户、SSO 和管理后台。
- 所有 Gateway Adapter 同时达到 Stable。
- 无监督高风险多 Agent 写入生产仓库。
- 自动生成并永久启用全局 Role/Skill。
- 在缺少调用图证据时进行大规模 Runtime 删除。

## 5. 产品成熟度

### Host

- Host Runtime：当前基础已存在，需回归和 Contract/E2E 验证。

### Plugin

- oh-my-deepagent：正式产品范围；当前成熟度必须按角色、编排、宿主集成和测试分别评估。
- “预装”不等于“已验证 Stable”。

### Gateway

- Gateway Core：v0.1 Stable 目标。
- Feishu：Stable 目标。
- 其他平台：按证据分级。

## 6. Phase 1 首要审计

1. 还原原始 OpenCode + oh-my-OpenAgent 插件架构。
2. 生成当前 DeepCode 生产入口调用图。
3. 生成 `packages/oh-my-deepagent` 内部调用图。
4. 将代码分类为：
   - Host Execution；
   - Plugin Orchestration；
   - Compatibility/Test；
   - Unused/Deprecated。
5. 对每项给出 Keep、Adapt、Bridge、Replace、Remove 建议。
6. 未完成以上工作前，不执行 Runtime 删除。

## 7. v0.1 Go/No-Go

- P0 安全缺陷为 0。
- Provider Contract 通过。
- 本地任务 E2E 通过。
- 插件角色与编排链路通过既定测试。
- Gateway Core 和飞书 E2E 通过。
- 宿主与插件的 Permission/Workspace 契约不可绕过。
- README Claim Evidence Coverage = 100%。

## 8. 冻结结论

v0.1 的收敛方式不是压扁插件架构，而是：

```text
保持宿主—插件共生关系
→ 识别真实执行边界
→ 保留编排价值
→ 修复安全和契约缺口
→ 建立测试证据
→ 再决定迁移或删除
```
