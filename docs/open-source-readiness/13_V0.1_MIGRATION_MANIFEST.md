## 1. 目的

本清单用于避免两类错误：

1. 因为代码存在独立 Runtime、Loop、Memory 或 Provider，就直接判定与宿主冲突。
2. 因为插件原本是共生关系，就忽略真实的安全绕过、状态分裂或重复维护问题。

## 2. 分类动作

| 动作 | 含义 |
|---|---|
| Keep | 保持现状，补文档和测试 |
| Adapt | 保留主体，适配宿主 Contract |
| Bridge | 通过 Adapter/Bridge 连接宿主和插件 |
| Replace | 用已验证实现替代，但保留原能力 |
| Remove | 确认无价值或被安全替代后删除 |
| Archive | 仅保留历史或研究材料 |
| Unknown | 证据不足，不执行迁移 |

## 3. 代码性质标签

每个组件还必须标记性质：

- Host Execution；
- Plugin Orchestration；
- Compatibility；
- Test Runtime；
- Transitional；
- Unused/Deprecated；
- Unknown。

动作和性质是两个维度。例如：

- `Plugin Orchestration + Keep`；
- `Compatibility + Bridge`；
- `Unused + Remove`。

## 5. 明确保留的产品能力

- 角色系统；
- Skill 系统；
- Planning；
- Role Routing；
- Plan → Build → Review；
- Subagent；
- Multi-Agent Orchestration；
- Gateway；
- Harness；
- 插件独立测试能力。

这些能力不得因“统一 Runtime”措辞而被删除。

保留目标能力不等于把它们写入 v0.1 Alpha 当前能力；未形成生产入口和 E2E 的组件保持 Not Integrated/Experimental。

## 6. 需要审计而非预删的边界

### 6.1 Provider

可能结论包括：

- Keep：插件确需独立 Provider Contract；
- Bridge：转接 Host Provider；
- Test Runtime：只用于 Mock/集成测试；
- Remove：无调用且无兼容用途。

### 6.2 ToolRunner

判断依据：

- 是否执行真实副作用；
- 是否经过 Permission/Workspace；
- 是否只是 Plugin Tool Adapter；
- 是否为独立测试工具。

### 6.3 MemoryStore

判断依据：

- 存储的事实类型；
- 是否与 Host History 重叠；
- 是否有父子 Task 映射；
- 重启恢复时谁是权威。

### 6.4 Transport

判断依据：

- 是否服务插件的标准安装形态；
- 是否用于开发、测试、Gateway 或远程兼容；
- 是否存在安全和维护风险。

## 7. Gateway 分类

### Keep

- Adapter Contract；
- Authentication；
- Replay/Idempotency；
- Identity/Workspace Mapping；
- Queue/Delivery；
- 平台特定 Parser/Formatter。

### Replace 或 Remove 候选

仅在证据确认后处理：

- 无鉴权入队路径；
- 错误 Adapter 回包；
- 无界 Queue；
- 无法取消的子进程桥；
- 已废弃且无调用的 Platform Adapter。

Gateway 是否通过 Host API、Plugin API 或 Bridge 调用，需在 v0.3 调用图后确定；目标是不复制安全和业务语义，而非禁止所有中间层。

## 8. Harness 分类

- 对真实执行有影响且可验证：Keep/Adapt。
- 仅记录日志但产品宣称 Enforcement：修正文案并补实现。
- 无调用：先标 Unknown，再决定 Archive/Remove。
- 研究模块：可保留 Experimental，不要求删除。

## 9. 删除门槛

任何删除必须同时满足：

1. 已生成所有调用方清单。
2. 已对照原始项目职责。
3. 已确认不是插件编排、兼容或测试基础设施。
4. 已确认无外部 API 使用者，或提供迁移方案。
5. 已有替代实现或确认无功能用途。
6. 角色、Subagent、Gateway 和安全回归测试通过。
7. 文档和 Release Notes 已说明。
8. 来源、许可证和第三方声明已审计。

## 10. 禁止的删除理由

以下理由单独使用时无效：

- “类名叫 Runtime”。
- “有自己的 Message Loop”。
- “有自己的 MemoryStore”。
- “Host 已经有类似模块”。
- “希望架构看起来只有一条线”。

必须证明实际职责重叠和产品无损。

## 12. 当前冻结结论

在 v0.2/v0.3 对应审计完成前：

- 不删除 AgentRuntime/runMessageLoop。
- 不删除插件 Provider、ToolRunner、MemoryStore 或 Transport。
- 不把它们写成正式生产能力，也不写成已确认重复。
- 只处理已有充分证据的 P0 安全问题。
