# DeepCode v0.1 产品架构

> 状态：Phase 0 已确认
> 目标：将 Runtime、Built-in DeepAgent 和 Gateway 组织为一个产品，而不是三个松散项目

## 1. 产品公式

```text
DeepSeek Model
+ DeepCode Runtime
+ Built-in DeepAgent
+ DeepCode Gateway
+ Evidence & Safety
= DeepCode v0.1
```

## 3. 用户入口

### 3.1 本地入口

用户在本地仓库中启动 DeepCode：

```text
安装
→ 配置 DeepSeek
→ 进入 Workspace
→ 选择 Role
→ 提交任务
→ 权限确认
→ 修改与验证
→ 证据输出
```

### 3.2 Gateway 入口

用户从消息平台进入同一产品：

```text
平台消息
→ 平台鉴权
→ 用户/Workspace Policy
→ Session Resolution
→ Role Resolution
→ DeepCode Runtime
→ 工具与权限
→ 原平台回包
```

Gateway 不创建另一种 Agent 产品，只改变消息入口和交互载体。

## 4. 用户画像

### Persona A：DeepSeek 开发者

目标：使用 DeepSeek 在真实仓库中完成编码任务，并看到模型、工具和验证证据。

### Persona B：移动或消息协作用户

目标：通过飞书等平台发起、继续和查看受控的 Coding Agent 任务，无需一直停留在终端。

边界：远程入口不能获得超出预配置 Workspace 和 Permission 的能力。

### Persona C：Agent 高级用户

目标：选择适合任务的预装角色，组合 Plan、Build、Review 和高级角色完成复杂工作。

### Persona D：开源贡献者和 Harness 研究者

目标：理解 Runtime、Role、Gateway 和 Harness 的真实作用路径，能够复现测试和扩展能力。

## 5. 核心 Job-to-be-Done

### JTBD-001 本地编码闭环

> 当我在本地仓库中处理 Bug、功能或重构时，我希望 DeepCode 能理解约束、执行最小修改、运行验证并给出证据。

### JTBD-002 选择专业 Agent

> 当任务类型不同，我希望选择预装的专业角色，而不需要安装另一个 Agent 项目或学习另一套 Runtime。

### JTBD-003 消息平台远程协作

> 当我离开终端或需要在团队沟通环境中发起任务时，我希望通过已授权平台访问同一个 DeepCode Session，并确保 Workspace 和权限不被绕过。

### JTBD-004 可验证 Harness

> 当 DeepCode 声称做了模型路由、约束保护或 Reasoning 管理时，我希望看到该决策是否真实应用以及对应证据。

## 7. 角色产品模型

### 7.1 角色是产品内能力，不是独立 Agent 应用

每个 Role 是以下对象的组合：

```text
Role Metadata
+ System Prompt
+ Allowed Tools
+ Required Skills
+ Runtime Policy
+ UX Metadata
+ Test Evidence
```

### 7.2 默认用户路径

- 默认进入 Build。
- 复杂任务可先进入 Plan。
- 完成后进入 Review。
- 用户可以显式选择高级角色。
- 自动选择是辅助能力，不能替代用户明确选择。

### 7.3 角色可见性

| 层级 | 角色 | 目的 |
|---|---|---|
| 核心 | Build / Plan / Review | 覆盖主要编码闭环 |
| 高级 | 其余预装角色 | 专业分析、探索、审查、视觉或创作任务 |

所有角色均随 DeepCode 安装。成熟度影响标签和文档，不影响“是否内置”。

## 8. Gateway 产品模型

### 8.1 Gateway Core 是 Stable 产品组件

Gateway Core 对所有 Adapter 提供统一：

- Auth Contract。
- Message Contract。
- Session Contract。
- Workspace Policy。
- Queue / Concurrency。
- Runtime Bridge。
- Delivery Result。
- Observability。

### 8.2 Adapter 是独立成熟度单元

平台发布状态按单个平台矩阵决定：

```text
Auth
+ Parser
+ Idempotency
+ Session Isolation
+ Outbound
+ Reconnect
+ E2E
= Adapter Maturity
```

### 8.3 首发平台策略

- 飞书：Stable 目标。
- 企业微信、Telegram、Slack：Beta 候选。
- 其他现有平台：保留并逐步补齐，未验证前标记 Experimental。

## 9. 产品级核心流程

### 9.1 本地代码任务

```text
User
→ Role
→ Intent / Constraints
→ Model Decision
→ Context
→ Tool Permission
→ Tool Execution
→ Test Evidence
→ Review
→ Completion
```

### 9.2 Gateway 代码任务

```text
Remote User
→ Adapter Auth
→ Identity / Workspace Policy
→ Existing or New Session
→ Role
→ Runtime
→ Permission Policy
→ Tool Execution
→ Delivery
```

对于远程入口，涉及 ask 的高风险操作必须有可执行的交互设计；不能因为平台不支持复杂确认而自动 allow。

### 9.3 Plan-Build-Review

```text
Plan: 目标、步骤、文件范围、验收
→ Build: 执行、工具、测试
→ Review: Diff、约束、测试、风险
→ User: 接受、继续或修正
```

三个角色共享 Session 和 Task，不复制上下文。

## 11. UX 要求

### 本地 UX

用户能看到：

- 当前 Workspace。
- 当前 Role。
- 当前 Provider / Model。
- reasoning effort。
- Tool 和 Permission。
- Test Evidence。

### Gateway UX

用户能看到：

- 当前绑定 Workspace。
- 当前 Session 和 Role。
- 是否需要权限确认。
- 任务状态。
- 结果摘要和完整结果入口。

### Role UX

- 核心角色优先展示。
- 高级角色可搜索和浏览。
- 显示角色用途、Tool 范围和成熟度。
- 切换角色前说明是否会影响模型或权限。

## 12. 产品边界

v0.1 不承诺：

- 任意互联网用户可访问 Gateway。
- 消息平台可以指定任意本地目录。
- 所有 Adapter 达到相同 SLA。
- 角色可以绕过统一 Permission。
- 多 Agent 默认并行执行高风险写操作。
- Harness 的研究假设自动等于产品收益。
